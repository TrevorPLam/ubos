## Research Roundup — P0‑I18N (2026‑05‑06)

### 1. react-i18next & i18next — Latest Versions & 2026 State

**react-i18next v17.0.6** (May 4, 2026) is the latest stable release. The v17 line is the current production version, with active maintenance and fixes. Meanwhile, **i18next core has reached v26.0.8** (April 25, 2026), reflecting a significant version gap between the React binding and the core library. Key i18next v26 breaking changes: removed legacy `interpolation.format` function (custom formatting must now use `i18next.services.formatter.add()`), removed deprecated `initImmediate` (use `initAsync` instead, renamed since v24), and removed `showSupportNotice`. For UBOS on Phase 0, react‑i18next v17.x with i18next v26.x is the recommended pairing — the core library is substantially more modern and performant than earlier versions.

**TypeScript improvements in v25.10.2**: `keyFromSelector` is now fully type-safe — the selector callback is constrained against resource definitions, catching invalid keys at compile time. v25.4.0 added a new `enableSelector` API (`"optimize"` mode) that dramatically improves IDE performance for large translation dictionaries without affecting build times.

**SSR requires careful coordination**: react‑i18next supports SSR via `I18nextProvider` with `initialI18nStore` and `initialLanguage` props. "By doing so the translations won't be loaded and initial clientside render will avoid any flickering or rerender by checksum mismatch." For TanStack Start specifically, community discussions confirm react‑i18next works with SSR support, but Paraglide JS has emerged as an alternative with first‑class TanStack Start integration via a Vite plugin that provides tree‑shaking and per‑page translation loading.

**Decision for UBOS**: Use react‑i18next v17.x + i18next v26.x. While Paraglide JS offers tree‑shaking benefits, react‑i18next has the larger ecosystem, more community resources, and a proven SSR compatibility pattern. The Intlayer benchmark (2026‑04‑20) confirms that "the main risk on TanStack Start is shipping unnecessary content: including translations for other pages and other locales in the same route's bundle." Namespace‑based loading and lazy‑loaded translation files mitigate this.

### 2. i18next Namespaces — Organization Pattern

Namespaces are "a feature in i18next internationalization framework which allows you to separate translations that get loaded into multiple files." The official documentation recommends organizing namespaces by:
- **common.json** — reused everywhere (button labels "save", "cancel", validation texts, glossary words)
- **Per‑view/page**: namespace per application section or feature set
- **Per‑module for lazy loading**: single page applications benefit from module‑scoped namespaces

For UBOS, the recommended namespace structure mirrors the domain architecture:
```
public/locales/
  en/
    common.json        — universal UI strings, shell components
    auth.json           — sign-in, sign-up, password reset
    crm.json            — CRM module
    projects.json       — Projects module
    documents.json      — Documents module
    finance.json        — Finance module
    assets.json         — Assets module
    portal.json         — Portal module
    analytics.json      — Analytics module
    settings.json       — Settings module
    dashboard.json      — Dashboard module
  ar/                   — mirrored structure for Arabic (RTL)
  he/                   — Hebrew (RTL)
  ...
```

At production scale, translation files in the repository become a bottleneck: "Merge conflicts. Two developers add keys to the same namespace. Every PR that touches translations conflicts with every other one." The resolution pattern is to decouple translation delivery from code delivery by loading translations at runtime from a CDN. For Phase 0, translation files live in the repository; the CDN pattern is documented as a Phase 1/2 upgrade path.

### 3. Tailwind CSS v4 RTL — Logical Properties Are Built In

Tailwind CSS v4 provides **first‑class RTL support** via CSS logical properties — no plugins, no custom CSS, no additional tooling required. The key mapping:

| Physical (LTR only) | Logical (LTR + RTL) | CSS Property |
|---|---|---|
| `ml-4` | `ms-4` | `margin-inline-start` |
| `mr-4` | `me-4` | `margin-inline-end` |
| `pl-4` | `ps-4` | `padding-inline-start` |
| `pr-4` | `pe-4` | `padding-inline-end` |
| `left-0` | `start-0` | `inset-inline-start` |
| `right-0` | `end-0` | `inset-inline-end` |
| `text-left` | `text-start` | `text-align: start` |
| `text-right` | `text-end` | `text-align: end` |
| `rounded-l-lg` | `rounded-s-lg` | `border-start-start-radius` |
| `rounded-r-lg` | `rounded-e-lg` | `border-start-end-radius` |
| `border-l` | `border-s` | `border-inline-start` |
| `border-r` | `border-e` | `border-inline-end` |

Symmetrical utilities (`px-4`, `mx-4`, `p-4`, `m-4`) apply to both sides and work correctly in RTL without changes. The `dir="rtl"` attribute on the `<html>` element triggers the browser to automatically compute the correct logical property values. "By using start and end, your layout 'just works' when the `dir='rtl'` attribute is applied. No extra classes needed."

**For Radix UI components** (Dropdowns, Popovers, Tooltips, Sliders): these render in portals outside the DOM tree and need explicit direction context. The solution, validated by the 2026‑05‑06 community article, is wrapping the application with Radix UI's `DirectionProvider`:

```tsx
import * as Direction from "@radix-ui/react-direction";
<Direction.Provider dir={currentDir}>
  <div dir={currentDir}>
    <AppContent />
  </div>
</Direction.Provider>
```

This ensures portalled components inherit the correct text direction automatically.

### 4. Intl API — Locale-Aware Formatting Without Libraries

The ECMAScript Internationalization API (`Intl`), available globally in all modern browsers, provides "a native way to handle locale- and culture-sensitive data and operations" without any third‑party libraries. The 2026‑02‑02 W3C guide confirms this is the recommended approach.

**Key `Intl` APIs for UBOS**:

| API | Purpose | Example |
|---|---|---|
| `Intl.DateTimeFormat` | Locale-aware dates/times | `new Intl.DateTimeFormat('ar-EG').format(new Date())` |
| `Intl.NumberFormat` | Numbers, currencies, units | `new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR' })` — positions symbol and spacing correctly |
| `Intl.RelativeTimeFormat` | "3 days ago" style | `new Intl.RelativeTimeFormat('fr').format(-3, 'day')` |
| `Intl.ListFormat` | "apple, banana, and cherry" | `new Intl.ListFormat('en').format(['apple', 'banana', 'cherry'])` |
| `Intl.Collator` | Locale-sensitive sorting | `['ä', 'a', 'z'].sort(new Intl.Collator('de').compare)` |

**Critical currency formatting note**: `Intl.NumberFormat` requires both `style: 'currency'` and an ISO 4217 currency code (`'USD'`, `'EUR'`). The position of the currency symbol and spacing are locale‑dependent — `Intl` handles this automatically, placing `$` before the number in `en‑US` and `€` after in `de‑DE`.

**Performance consideration**: "Creating a new `Intl.DateTimeFormat` object for every format call is expensive. Cache the formatter instance and reuse it." The UBOS `format.ts` wrapper should create cached formatter instances keyed by locale + options.

### 5. Language Direction — The Single Source of Truth Pattern

The 2026‑05‑06 community architecture article ("Beyond Translation: Mastering RTL Layouts with i18next and Radix UI") establishes a three‑layer RTL architecture that UBOS should follow:

**Layer 1 — Language configuration**: Each supported language includes a `dir` property (`"ltr"` or `"rtl"`) alongside its code and label. This is the single source of truth for direction.

**Layer 2 — DOM synchronization**: Listen to i18next's `languageChanged` event and automatically set `document.documentElement.dir` and `document.documentElement.lang`. This binds language switching and layout direction — no manual coordination needed.

**Layer 3 — Tailwind logical properties**: Replace all physical direction classes (`ml-*`, `pl-*`, `left-*`, `text-left`) with logical equivalents (`ms-*`, `ps-*`, `start-*`, `text-start`). Symmetrical utilities (`px-*`, `mx-*`) are unaffected.

This is the same architecture confirmed by the 4‑billion‑user i18n guide published on 2026‑05‑06: "This system is divided into three layers: the language configuration layer, the DOM synchronization layer, and the component adaptation layer. Each layer does only one thing, but missing one layer causes collapse."

### 6. Paraglide JS Alternative — Noted for Future Evaluation

Paraglide JS provides first‑class TanStack Start support and is "part of TanStack's CI pipeline." It offers tree‑shakable translations, type‑safe message functions, and a Vite plugin for automatic configuration. However, the community is smaller, documentation is sparse, and the migration from react‑i18next requires converting all translation JSON files to the Paraglide format.

For UBOS Phase 0, react‑i18next is selected for its ecosystem maturity and proven SSR pattern. Paraglide JS should be re‑evaluated in Phase 2 when bundle size optimization becomes critical — the benchmark data from Intlayer (2026‑04‑20) suggests significant bundle size advantages for tree‑shaken translations.

**(f) Package structure**: Create `packages/i18n/` as a shared workspace package with its own `package.json` and `tsconfig.json`. // Before
```typescript
<Button>Save Changes</Button>

// After
<Button>{t('common:button.saveChanges')}</Button>
```

```typescript
// Before
toast.success(`Lead "${leadName}" created successfully`)

// After
toast.success(t('crm:toast.leadCreated', { name: leadName }))
```

**(c) Extraction order — by priority**:
1. **Shell components** (Header, Sidebar, MainLayout, CommandPalette) — these are visible on every page
2. **Auth pages** (SignIn, SignUp) — user‑facing entry points
3. **CRM module** — the only fully functional domain; highest user impact

5. **Settings page** — user management, integrations
6. **Remaining domain pages** (Projects, Documents, Finance, Assets, Portal, Analytics)
7. **56 shadcn/ui components** — shared primitives with aria‑labels and button text

**(d) Translation key naming convention**: `{namespace}:{category}.{key}` with camelCase for the key:
- `common:button.save`, `common:button.cancel`, `common:button.delete`
- `crm:lead.create`, `crm:lead.edit`, `crm:toast.leadCreated`
- `auth:signIn.title`, `auth:signIn.emailPlaceholder`
- `dashboard:kpi.revenue`, `dashboard:kpi.activeProjects`

Keys use natural language descriptions — not opaque IDs. This makes translation files self‑documenting and easier for translators to understand without access to the source code.

**(e) shadcn/ui components**: Most shadcn/ui components contain minimal user‑facing text (aria‑labels like "Close dialog", button text like "Previous", "Next"). These go in the `common` namespace. Components with internal strings (empty states, loading messages) use the `common` namespace as well.

**(f) Validation**: After extraction, a manual audit verifies that no hardcoded English strings remain visible in the application. A CI check (or lint rule) flags any `t()` call with a key not present in the English translation files.

### [ ] P0-I18N-3: Implement locale‑aware number, date, and currency formatting

**Status:** ⏳ Not Started
**Actor:** AGENT
**Priority:** 🟡 Medium
**Current State:** All number, date, and currency formatting in the UBOS application uses JavaScript defaults (e.g., `date.toLocaleDateString()`, hardcoded `$` prefix for currency). These do not adapt to the user's locale. For non‑English users, dates render in US format, numbers use period decimal separators, and currency symbols are always USD. The `date-fns` library is already used for mock data calculations but is not wrapped in locale‑aware formatters.
**Size:** Medium

**Description:**
Create `apps/web/src/lib/format.ts` — a utility module that wraps the ECMAScript `Intl` API for locale‑aware number, date, currency, and list formatting. This module is the single entry point for all formatting in the application — developers never call `Intl` APIs directly.

**(a) Cached formatter instances**: Creating `Intl` formatters is expensive — "creating a new `Intl.DateTimeFormat` object for every format call is expensive. Cache the formatter instance and reuse it." The `format.ts` module implements a `Map`‑based cache keyed by `locale:options` to memoize formatter instances. Cache size is bounded to prevent memory leaks.

**(b) Number formatting**: `formatNumber(value, options?)` — wraps `Intl.NumberFormat`. Accepts `style` ('decimal', 'percent'), `minimumFractionDigits`, `maximumFractionDigits`. Reads the current locale from i18next (`i18n.language`). Defaults to the user's locale. Example: `formatNumber(1234567.89)` → `"1,234,567.89"` (en‑US) or `"1.234.567,89"` (de‑DE).

**(c) Currency formatting**: `formatCurrency(value, currency, options?)` — wraps `Intl.NumberFormat` with `style: 'currency'`. The `currency` parameter is an ISO 4217 code (`'USD'`, `'EUR'`, `'GBP'`). The locale determines symbol position and spacing — `Intl` handles this automatically. Example: `formatCurrency(1000, 'EUR')` → `"€1,000.00"` (en‑US) or `"1.000,00 €"` (de‑DE). For the Finance module specifically, the currency should match the organization's configured currency, not the user's locale.

**(d) Date formatting**: `formatDate(date, options?)`, `formatTime(date, options?)`, `formatDateTime(date, options?)`, `formatRelative(date, options?)`. Wraps `Intl.DateTimeFormat` and `Intl.RelativeTimeFormat`. Provides shorthand presets: `formatDate(date, { preset: 'long' })` for "May 6, 2026", `formatDate(date, { preset: 'short' })` for "5/6/26". Accepts custom options for full control.

**(e) List formatting**: `formatList(items, options?)` — wraps `Intl.ListFormat`. Automatically handles conjunction style differences between languages. Example: `formatList(['CRM', 'Projects', 'Documents'])` → `"CRM, Projects, and Documents"` (en) or `"CRM, Projects und Documents"` (de).

**(f) Number abbreviation**: `formatCompactNumber(value)` — wraps `Intl.NumberFormat` with `notation: 'compact'`. Example: `formatCompactNumber(1500000)` → `"1.5M"`.

**(g) Integration with date-fns**: For date calculations and manipulations that go beyond formatting (e.g., "30 days from now"), the existing `date-fns` library remains in use. The `formatDate()` utility should accept a `Date` object, which `date-fns` functions produce.

### [ ] P0-I18N-4: Configure RTL layout support in Tailwind and component library

**Status:** ⏳ Not Started
**Actor:** AGENT
**Priority:** 🟡 Medium
**Current State:** The UBOS application uses Tailwind CSS v4 physical direction classes (`ml-*`, `pl-*`, `left-*`, `text-left`, `rounded-l-*`) throughout all 56 UI components, the shell layout, and the nine domain pages. There is no `dir="rtl"` support on the `<html>` element, no language direction configuration in the i18n setup, and no Radix UI `DirectionProvider`. Adding an RTL language (Arabic, Hebrew) would require manually overriding hundreds of CSS classes — a maintenance nightmare.
**Size:** Medium

**Description:**
Configure RTL layout support using the three‑layer architecture validated by the 2026‑05‑06 community: language configuration → DOM synchronization → logical properties. This enables automatic layout mirroring for RTL languages without per‑component overrides.

**(a) Language direction configuration (Layer 1)**: Extend the i18n configuration in `packages/i18n/src/index.ts` with a supported languages array that includes the `dir` property:
```typescript
export const SUPPORTED_LANGUAGES = [
  { code: 'en', label: 'English', dir: 'ltr' },
  // Future languages added here:
  // { code: 'ar', label: 'العربية', dir: 'rtl' },
  // { code: 'he', label: 'עברית', dir: 'rtl' },
] as const;
```

This is the single source of truth for language direction — every component that needs direction information reads from this configuration, not from a hardcoded assumption.

**(b) DOM synchronization (Layer 2)**: Listen to i18next's `languageChanged` event and automatically set `document.documentElement.dir` and `document.documentElement.lang`:
```typescript
i18n.on('languageChanged', (lng) => {
  const lang = SUPPORTED_LANGUAGES.find(l => l.code === lng);
  document.documentElement.dir = lang?.dir || 'ltr';
  document.documentElement.lang = lng;
});
```

This eliminates manual coordination — when the user switches languages, the layout direction updates automatically. For SSR, the initial `dir` and `lang` attributes are set on the server‑rendered HTML.

**(c) Tailwind logical properties (Layer 3)**: Migrate physical direction classes to logical equivalents across the codebase. This is a systematic replacement:

| Physical Class | Logical Class | Scope |
|---|---|---|
| `ml-*` | `ms-*` | Margin inline start |
| `mr-*` | `me-*` | Margin inline end |
| `pl-*` | `ps-*` | Padding inline start |
| `pr-*` | `pe-*` | Padding inline end |
| `left-*` | `start-*` | Inset inline start |
| `right-*` | `end-*` | Inset inline end |
| `text-left` | `text-start` | Text alignment start |
| `text-right` | `text-end` | Text alignment end |
| `rounded-l-*` | `rounded-s-*` | Border start radius |
| `rounded-r-*` | `rounded-e-*` | Border end radius |
| `border-l-*` | `border-s-*` | Border inline start |
| `border-r-*` | `border-e-*` | Border inline end |

Symmetrical utilities (`px-*`, `mx-*`, `py-*`, `my-*`, `p-*`, `m-*`) apply to both sides and require no changes. This migration applies to all 56 shadcn/ui components, the shell layout, and the nine domain pages.

**(d) Radix UI DirectionProvider (Layer 3 — Component Adaptation)**: Wrap the application with Radix UI's `DirectionProvider` to ensure portalled components (Dropdowns, Popovers, Tooltips, Sliders) inherit the correct direction:
```tsx
import * as Direction from "@radix-ui/react-direction";
<Direction.Provider dir={currentDir}>
  <div dir={currentDir}>
    <AppContent />
  </div>
</Direction.Provider>
```

This is essential — Radix UI components render outside the DOM tree in portals, so the `<html>` `dir` attribute does not propagate to them. `DirectionProvider` fills this gap by explicitly passing the direction context.

**(e) LTR‑only overrides**: For elements that must remain LTR even in RTL layouts (e.g., code blocks, URLs, certain numeric data displays), add `dir="ltr"` explicitly on those elements. This is the standard pattern for bidirectional content.

**Research Findings (2026‑05‑06):**
- Tailwind CSS v4 provides first‑class RTL support via logical properties — no plugins needed
- Radix UI needs `DirectionProvider` for portalled components to inherit direction
- The three‑layer architecture (language config → DOM sync → logical properties) is the production‑proven 2026 pattern
- "By using start and end, your layout 'just works' when the `dir='rtl'` attribute is applied"
- Symmetrical utilities (`px-*`, `mx-*`) work unchanged in RTL
